# SunX Trading Bot — اسکلت کامل

ربات معاملاتی خودکار برای SunX. مستقل از MCP اجرا می‌شود و مدل زبانی در حلقهٔ
معامله نیست. تمام اعداد از API زندهٔ `api.sunx.io` می‌آیند.

## چرا جدا از MCP

ابزار MCP فقط وقتی اجرا می‌شود که یک مدل زبانی در گفتگو تصمیم بگیرد صدایش بزند.
ربات باید ۲۴ ساعته و قطعی کار کند. پس:

- **این ربات:** WebSocket زنده → وضعیت → استراتژی → موتور ریسک → سفارش REST
- **سرور MCP (پروژهٔ جدا):** برای پرسیدن وضعیت و خاموش کردن دستی

## لایه‌ها

| فایل | کار |
|---|---|
| `bot/config.py` | محدودیت‌های سخت ریسک از `.env` |
| `bot/signing.py` | امضای HmacSHA256 و Ed25519 مطابق مستندات |
| `bot/rest.py` | فراخوانی‌های REST |
| `bot/feed.py` | WebSocket عمومی و خصوصی، اتصال مجدد، ضربان قلب |
| `bot/state.py` | وضعیت زندهٔ بازار، پوزیشن و حساب |
| `bot/risk.py` | موتور ریسک. استراتژی نمی‌تواند دورش بزند |
| `bot/deadman.py` | کلید مرگ روی `/sapi/v1/trade/cancel-after` |
| `bot/executor.py` | ارسال سفارش، حالت کاغذی، ژورنال |
| `bot/strategies/` | استراتژی به‌صورت قطعهٔ قابل تعویض |
| `bot/runner.py` | اتصال همه و حلقهٔ اصلی |
| `tools/pick_contract.py` | انتخاب نماد مناسب سرمایه از دادهٔ زنده |

## چه چیزی واقعاً تست شده

- **۱۸ تست واحد** روی موتور ریسک، اجراکننده و استراتژی (`tests/test_bot.py`).
- **امضا:** متن پیش از امضا با مثال مرحلهٔ ۶ مستندات یکسان است.
- **اجرای زنده:** ربات روی JST-USDT با دادهٔ واقعی WebSocket اجرا شد؛ اسپرد
  ۰.۰۷۱٪، بدون قطع اتصال.
- **محافظ سرمایه:** با ۱۵ دلار و اهرم ۳، درخواست معاملهٔ BTC **رد شد** چون یک
  قرارداد BTC حدود ۷۸ دلار است.

## گام ۱ — نصب

```
cd مسیر\پوشه\sunx-bot
pip install -r requirements.txt
```

## گام ۲ — انتخاب نماد

این مهم‌ترین تصمیم است. با سرمایهٔ کم، اسپرد تعیین‌کننده است:

```
python tools\pick_contract.py --capital 15 --leverage 3 --min-contracts 5 --max-spread 0.3
```

## گام ۳ — تنظیمات

`.env.example` را کپی کنید و نامش را `.env` بگذارید. کلیدهای API را داخلش
بنویسید. محدودیت‌های ریسک از قبل محافظه‌کارانه تنظیم شده‌اند.

## گام ۴ — بررسی قبل از پرواز

```
python run_bot.py --preflight
```

این دستور **هیچ سفارشی نمی‌فرستد**. فقط چک می‌کند: نماد قابل معامله است،
چند قرارداد با سرمایه‌تان می‌خرید، کارمزد واقعی حساب شما چقدر است، و حداقل
حرکت لازم برای سوددهی چند درصد است. اگر `"ready": false` دید، مشکل‌ها را
در `problems` نوشته.

## گام ۵ — حالت کاغذی

```
python run_bot.py
```

استراتژی روی دادهٔ واقعی اجرا می‌شود ولی **هیچ سفارشی به صرافی نمی‌رود**.
همه‌چیز در `data/orders.jsonl` ثبت می‌شود و وضعیت لحظه‌ای در `data/status.json`.

**حداقل یک هفته کاغذی بگذارید.** بعد در ژورنال ببینید چند معامله زده، چند
درصد سودده بوده، و آیا بعد از کارمزد چیزی باقی می‌ماند.

## گام ۶ — معاملهٔ واقعی

فقط وقتی نتیجهٔ کاغذی قابل قبول بود. در `.env`:

```
BOT_LIVE=1
```

## محافظت‌ها

| محافظ | کار |
|---|---|
| موتور ریسک | هر سفارش از آن می‌گذرد. رد شدن قطعی است |
| کلید مرگ | اگر ربات کرش کند، صرافی خودش سفارش‌ها را لغو می‌کند |
| سقف ضرر روزانه | به سقف برسد، ربات متوقف می‌شود |
| سقف اهرم | اهرم مؤثر محاسبه و محدود می‌شود |
| حد ضرر و سود | پوزیشن خودکار بسته می‌شود |
| سقف زمان نگهداری | پیش‌فرض ۳ ساعت |
| محدودیت نرخ سفارش | جلوی حلقهٔ معیوب را می‌گیرد |
| تشخیص دادهٔ کهنه | اگر WebSocket ۱۰ ثانیه ساکت بماند، سفارش رد می‌شود |
| شناسهٔ یکتای سفارش | تلاش مجدد بعد از خطای شبکه پوزیشن دوم نمی‌سازد |

## کلید مرگ

ربات هر ۵ ثانیه تایمر `cancel-after` را تمدید می‌کند. اگر ربات کرش کند، سرور
ریبوت شود یا اینترنت قطع شود، صرافی پس از ۱۵ ثانیه **خودش** همهٔ سفارش‌های
باز را لغو می‌کند. اگر پوزیشن باز باشد و کلید مرگ مسلح نباشد، ربات خودش را
متوقف می‌کند.

## محدودیت‌ها

- استراتژی `momentum` یک **نمونهٔ مرجع** است تا اسکلت قابل اجرا باشد. مزیت
  اثبات‌شده ندارد. استراتژی واقعی را باید بنویسید و بک‌تست کنید.
- بک‌تست در این نسخه نیست. دادهٔ کندل از `klines()` قابل گرفتن است.
- امضای WebSocket خصوصی مطابق مستندات پیاده شده ولی بدون کلید واقعی تست نشده.
  مسیر امضا `/ws/v1` است؛ اگر رد شد، `ws_sign_path` در `bot/feed.py` را عوض کنید.
